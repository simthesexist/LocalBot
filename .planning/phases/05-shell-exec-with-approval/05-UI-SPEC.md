## Surface Inventory

This phase introduces two new visible surfaces on top of the existing chat shell + sidebar. Each entry lists the surface ID, its location relative to the existing layout, and the sub-elements it owns.

### S1. Approval Modal Stack (UI-04)

- **Location:** Overlays the entire Electron window (`position: fixed; inset: 0`) at `z-index: 1500` — above the chat composer (default z-auto), above the AppModal primitive's default z-index (1000), above the DeleteConfirmModal (1100), above the BotSettingsPage (none — it's a route, not a modal). The backdrop is dimmed (`rgba(0, 0, 0, 0.4)`) reusing the Phase 4 `.modal-backdrop` rule.
- **Behavior:** One `<ApprovalModal>` per pending approval in the store. The stack renders them in arrival order; each newer modal stacks on top by 100 z-index steps (so modal #1 = 1500, modal #2 = 1600, modal #3 = 1700, …). When the topmost modal responds, the next one surfaces automatically.
- **Sub-elements (per modal):**
  - `ApprovalHeader` — title "Approve shell command" + close button (×). Clicking the close button is treated as "Deny" per the per-call approval contract (matches Phase 4 DeleteConfirmModal pattern).
  - `ApprovalPrompt` — single line: `The bot wants to run this command:` (color `--color-text-muted`, font 14 px).
  - `CommandPreview` — a `<pre>` showing the command verbatim (NO redaction in the modal — the user must see what they're approving), wrapped at 16 px padding, font `--font-mono` 12 px, background `--color-code-bg`, max-height 240 px, overflow-y auto.
  - `ApprovalWarning` — two short lines: `Allowing runs the command with your user privileges.` (regular) + `Always Allow saves the command so it can run without prompting in the future.` (regular; the words "Allowing" and "Always Allow" lead-in are bolded at 14 px semibold).
  - `ApprovalMeta` — single line: `Requested at HH:MM:SS` (color `--color-text-muted`, font 12 px). The bot name appears next to the timestamp: `Bot: <name>`.
  - `ApprovalButtonRow` — three buttons laid out left-to-right:
    - **Allow once** — primary (background `--color-accent`, text white, height 36 px, padding 0 16 px, border-radius 8 px). Pressing Enter while focus is anywhere in the modal activates this button (default focus on mount per the AppModal primitive).
    - **Always allow** — secondary (background `#f3f4f6`, text `--color-text`, border 1 px `--color-border`, same dimensions as primary). Pressing the keyboard shortcut `Shift+Enter` activates this button.
    - **Deny** — destructive (background `--color-stop-bg`, text white, same dimensions). Pressing the keyboard shortcut `Escape` activates this button (matches the AppModal primitive's existing Escape-to-close behavior; "Deny" is the safe default on close).
  - **No footer, no other rows.**

### S2. Shell Stream Block (UI-04 inline)

- **Location:** Inline within an existing assistant `MessageBlock` in the chat — same row as the `tool_use` block that invoked it. Visually distinct from regular tool_result blocks: dark slate background (`--lb-shell-bg`), monospace font, 1 px border (`--lb-shell-border`).
- **Sub-elements (per block):**
  - `ShellStreamHeader` — a single-row header strip with the badge `exec_command` (light indigo text on dark header background, font 11 px semibold, padding 4 px 8 px, border-radius 4 px) and the truncated command preview (`command.slice(0, 80)` followed by `…` if length > 80 — matches the audit-minimization pattern from RESEARCH §Pitfall 3). Right side shows live status: `Running…` while `exitCode === null`, switches to `Exit N · 1.2s` when `shell:exit` arrives.
  - `ShellStreamStdout` — a `<pre>` with `data-testid="shell-stdout"` showing accumulated stdout. Grows incrementally as `shell:token` events arrive. While the stream is open (`exitCode === null`), a blinking `▍` cursor (`--lb-shell-cursor`) is appended on the last line. Padding 8 px 12 px. Max-height 240 px; overflow-y auto (the existing chat scroll handles overflow, but capping at 240 px prevents a runaway `npm install` from pushing other blocks offscreen).
  - `ShellStreamStderr` — a `<pre>` with `data-testid="shell-stderr"` showing accumulated stderr (same styling as stdout but with `--lb-shell-stderr-text`). Only renders if stderr is non-empty.
  - `ShellStreamFooter` — a single-row footer strip (background `--lb-shell-footer-bg`, padding 4 px 12 px, font 11 px `--color-text-muted`-equivalent: `#9ca3af` on dark). Shows `Exit code: <N>` (left) and `Duration: <1.2s>` (right). Hidden until `shell:exit` arrives.
  - `ShellStreamAutoAllowNote` — a single-row indicator strip (background `--lb-auto-allow-bg`, border 1 px `--lb-auto-allow-border`, padding 4 px 12 px, font 12 px italic, color `--lb-auto-allow-text`). Shows ONLY when the audit line's `approvedBy === 'user-always'`. Reads: `Auto-approved from always-allow list (exact match).` Renders BETWEEN the header and the stdout (above the live stream) so the user has context for why no modal popped.

### S3. Denylist-Blocked Inline Indicator (UI-04 / SEC-03)

- **Location:** Inline within the same tool_result block that the `exec_command` tool_use would normally produce. Replaces the standard tool_result rendering (not an additional block).
- **Sub-elements:**
  - **No header badge** — the existing tool_result rendering is preserved but the body is replaced.
  - `DenylistStrip` — a single full-width strip (background `--lb-deny-badge-bg`, border 1 px `--lb-deny-badge-border`, padding 8 px 12 px, font 13 px, color `--lb-deny-badge-text`, font-weight 600) with two lines:
    - Line 1: `Blocked by global denylist`
    - Line 2: `<rule>` — the matched rule's human reason (e.g. `sudo elevates to root`).
  - `CommandExcerpt` — a `<pre>` (background `--color-code-bg`, font `--font-mono` 12 px, padding 8 px 12 px, max-height 120 px, overflow-y auto) showing the command verbatim (NO redaction — the user needs to see what was blocked to fix the prompt).

### S4. Composer Disabled State (UI-04)

- **Location:** The bottom-of-chat Composer.
- **Behavior:** When `pendingApprovals.size > 0`, the textarea gets `disabled={true}` and the send button is replaced with `disabled={true}` on the placeholder. The placeholder text changes from `Send a message to <bot>…` to `Approve the pending shell command before sending another message…`. The Stop button remains enabled (the user can still cancel the in-flight LLM turn while a modal is up — the modal just blocks NEW messages).

### S5. Approval Modal Stack Behavior

- **Trigger:** the daemon's `shell:request-approval` notification (a new IPC channel — see §IPC Events). Main proxies it to the renderer via `EVENT_SHELL_REQUEST_APPROVAL`.
- **Stack rules:**
  - At most one `<ApprovalModal>` per `shellId` (deduplication in the store keyed by `shellId`).
  - Modal #N has `z-index = 1500 + (N - 1) * 100` — so they stack visibly.
  - The topmost modal is the one the user interacts with; underneath modals have `pointer-events: none` so backdrop clicks land on the topmost.
  - When the topmost modal responds, it's removed from `pendingApprovals`; the next modal's backdrop becomes clickable; the visual stack collapses.

## Interaction Spec

### I1. Keyboard Shortcuts

| Shortcut | Surface | Behavior |
|----------|---------|----------|
| `Enter` | ApprovalModal (any focus) | Activates "Allow once" (default button per AppModal primitive) |
| `Shift+Enter` | ApprovalModal | Activates "Always allow" |
| `Escape` | ApprovalModal | Treated as "Deny" (matches AppModal primitive's existing Escape close; the close path is wired to `onRespond(shellId, 'deny')`) |
| `Tab` / `Shift+Tab` | ApprovalModal | Cycles focus through Allow once → Always allow → Deny → (back to first) per AppModal's existing focus trap |
| `Escape` | Chat composer (existing) | Cancels streaming — UNCHANGED from Phase 1 |
| No global shortcuts | — | ApprovalModal does not register any application-level shortcuts |

### I2. Focus Order

When a new `<ApprovalModal>` mounts (top of stack):

1. "Allow once" button (default focus per AppModal primitive).
2. "Always allow" button.
3. "Deny" button.
4. The × close button (per AppModal primitive).

Tab cycles within the modal; the AppModal primitive's focus trap prevents Tab from leaving the modal. The chat composer's textarea remains in the DOM but `disabled={true}` while `pendingApprovals.size > 0`.

When a shell-stream block mounts inline in the message list: no focus change (it appears at the bottom of the scroll position; the existing message-list auto-scroll handles positioning).

### I3. Click Targets

| Target | Minimum Size | Notes |
|--------|--------------|-------|
| ApprovalModal "Allow once" button | 36 px tall × ~96 px wide | Matches existing `.modal-button.primary` |
| ApprovalModal "Always allow" button | 36 px tall × ~110 px wide | Matches existing `.modal-button.secondary` |
| ApprovalModal "Deny" button | 36 px tall × ~64 px wide | Matches existing `.destructive` button class |
| ApprovalModal × close button | 24 × 24 px | Matches AppModal primitive's existing close button |
| Shell-stream block | 24 px tall header + variable body | Not interactive beyond scroll |
| Denylist-blocked strip | not interactive | Read-only inline indicator |
| Composer textarea | (existing) | Disabled while `pendingApprovals.size > 0` |

### I4. Debounce Windows

| Surface | Window |
|---------|--------|
| shell:token accumulation in renderer | 0 ms (every token updates the `<pre>` immediately per `shell:token` event) |
| shell-stream block re-render | Batched via React's automatic batching; no manual debounce |
| Composer re-enable after modal closes | 0 ms (immediate on `pendingApprovals.size === 0`) |
| Approval modal mount | 0 ms (synchronous on `shell:request-approval` notification arrival) |

### I5. Refresh Behavior

- The shell-stream block subscribes to `shell:token` and `shell:exit` events keyed by `shellId`. Subscriptions are wired in `useEffect` on mount and torn down on unmount (the block unmounts when its parent assistant message is removed from the message list, e.g. session switch).
- The approval modal subscribes to `shell:request-approval` at the App-level store (`state/shells.ts`). Subscriptions are wired once per app lifecycle.
- The denylist-blocked strip is stateless — it's a one-shot render of the tool_result payload; no refresh needed.

### I6. Modal Stacking (Concurrent Approvals)

When the LLM issues two `exec_command` calls in the same tool_use turn (parallel function calling):

- Each call gets its own `shellId` (UUID v4 generated by the daemon).
- The renderer maintains `pendingApprovals: Map<shellId, {command, requestAt, bot}>` in `state/shells.ts`.
- The `<ApprovalModalStack>` component renders one `<ApprovalModal>` per entry, in arrival order.
- Modal #N has `z-index = 1500 + (N - 1) * 100`.
- The topmost modal is interactive; modals #1..N-1 have `pointer-events: none` on their backdrops so the user's click goes through to the topmost modal.
- When the topmost modal responds, it's removed from `pendingApprovals`. The store change triggers a re-render; modal #N (now topmost) becomes interactive.
- This pattern matches Phase 4's existing modal-stack handling in `App.tsx` + `NewBotModal` + `DeleteConfirmModal` (where `DeleteConfirmModal` sits at z-index 1100 on top of `NewBotModal` at 1000).

## Component Decomposition

### D1. `src/renderer/components/ApprovalModal.tsx` (NEW)

```typescript
export interface ApprovalModalProps {
  shellId: string;
  command: string;
  requestAt: string;        // ISO
  bot: string;              // bot display name
  /** Computed z-index: 1500 for the first modal in the stack, +100 per additional. */
  zIndex: number;
  onRespond: (shellId: string, decision: 'allow-once' | 'allow-always' | 'deny') => void;
  onClose: () => void;      // treated as 'deny'
}
```

**Internal state:** none (props-driven).
**Renders:** `<AppModal title="Approve shell command" zIndex={zIndex} cardClassName="approval-modal" ariaLabel="Approve shell command execution">` wrapping:
- `<p>` prompt (`The bot wants to run this command:`)
- `<pre className="approval-modal-command" data-testid="approval-modal-command">{command}</pre>`
- `<div className="approval-modal-warning">` containing two `<p>` lines
- `<div className="approval-modal-meta">` containing `Bot: <name> · Requested at HH:MM:SS`
- `<div className="approval-modal-buttons">` containing three `<button>` elements with `data-testid="approval-modal-allow-once"`, `…-allow-always`, `…-deny`

## IPC Events

Five new event channels extend the locked Phase 1 IPC contract (D-07). Existing channels are not renamed.

### E1. `shell:request-approval` (main → renderer)

- **Trigger:** daemon's `tools/call exec_command` reaches the approval gate (after denylist passes + always-allow misses); the daemon issues a `shell/approve` JSON-RPC call (new method); main proxies it to the renderer.
- **Payload:**
  ```typescript
  export interface ShellRequestApprovalEvent {
    shellId: string;
    command: string;
    bot: string;
    requestAt: string;       // ISO
  }
  ```

### E2. `shell:respond` (renderer → main, invoke)

- **Trigger:** the user clicks Allow once / Always allow / Deny (or closes via Escape / × button).
- **Payload request:**
  ```typescript
  export interface ShellRespondRequest {
    shellId: string;
    decision: 'allow-once' | 'allow-always' | 'deny';
  }
  ```
- **Payload response:**
  ```typescript
  export interface ShellRespondResult {
    ok: boolean;
    error?: string;
  }
  ```
- **Main-side handler:** `src/main/ipc/shells.ts` (NEW) resolves the pending `shell/approve` JSON-RPC call back to the daemon. The daemon's `tools/call exec_command` resumes or throws `code: 'denied'`.

### E3. `shell:token` (main → renderer)

- **Trigger:** daemon's `exec_command.cjs` line-buffered readline emits each line.
- **Payload:**
  ```typescript
  export interface ShellTokenEvent {
    shellId: string;
    stream: 'stdout' | 'stderr';
    delta: string;           // includes trailing newline
  }
  ```

### E4. `shell:exit` (main → renderer)

- **Trigger:** daemon's `exec_command.cjs` `child.once('exit', ...)` fires (or abort fires).
- **Payload:**
  ```typescript
  export interface ShellExitEvent {
    shellId: string;
    exitCode: number | null;
    signal: string | null;   // 'SIGTERM' on POSIX abort; null on natural exit
    durationMs: number;
    stdoutBytes: number;     // for the audit line + footer (display only if exitCode === 0)
    stderrCount: number;     // for the audit line
    isError: boolean;        // exitCode !== 0 OR signal !== null OR abort
  }
  ```

### E5. `shell:aborted` (main → renderer, optional — same payload as `shell:exit` with `signal: 'SIGTERM'`)

- Per the RESEARCH decision, `shell:exit` carries the abort signal in its `signal` field. No separate `shell:aborted` channel is needed.

### E6. New IPC channels (CHANNELS additions in `src/shared/ipc-channels.ts`)

```typescript
SHELLS_RESPOND: 'shells:respond',           // renderer -> main (invoke)
EVENT_SHELL_REQUEST_APPROVAL: 'shell:request-approval',  // main -> renderer (event)
EVENT_SHELL_TOKEN: 'shell:token',            // main -> renderer (event)
EVENT_SHELL_EXIT: 'shell:exit',             // main -> renderer (event)
```

## Accessibility

- **Approval modal ARIA:**
  - `role="dialog"`, `aria-modal="true"`, `aria-labelledby` on the title (already handled by AppModal primitive).
  - The three buttons carry `aria-label` matching their visible text: `aria-label="Allow shell command once"`, `aria-label="Always allow this shell command"`, `aria-label="Deny shell command"`.
  - The `<pre>` command preview is marked `aria-readonly="true"` (defensive; users cannot edit it).
  - Focus trap active while open (inherited from AppModal primitive).
  - `aria-live="polite"` on the meta line (`Bot: <name> · Requested at HH:MM:SS`) so screen readers announce it on mount.
- **Shell stream block ARIA:**
  - The block carries `role="region"` + `aria-label="Shell command output: <command.slice(0, 40)>"`.
  - The `▍` cursor is hidden from screen readers via `aria-hidden="true"` (it has no semantic value).
  - The status line (`Running…` / `Exit N · 1.2s`) carries `aria-live="polite"` so screen readers announce the exit transition.
- **Denylist-blocked strip ARIA:**
  - `role="alert"` (the inline indicator IS a security event).
  - `aria-live="assertive"` so screen readers interrupt current speech to announce the block.
- **Keyboard accessibility:** every interactive element is reachable via Tab. The three buttons are the only Tab stops inside the approval modal. The shell-stream block has no interactive children (it's a read-only display).
- **Contrast:** all new color tokens pass WCAG AA for body text (audit in §Color). The dark shell-stream palette is tested at the same 4.5:1 body-text threshold as the light palette.
- **No reliance on color alone:** every state (running vs exited, error vs success, denylist-blocked vs allowed) carries BOTH a color AND a text label.

## Empty / Error / Loading States

### L1. Approval Modal

- **Loading:** not applicable (modal renders synchronously on the event).
- **Empty:** the daemon never requests approval for an empty command (defensive guard at the daemon); if it ever does, the `<pre>` shows the empty string with no placeholder.
- **Error:** if the renderer cannot reach main (`window.localbot.shell.respond` rejects), the modal stays open and the "Allow once" / "Always allow" / "Deny" buttons remain enabled for retry. The renderer console logs the error but does not surface it to the user — the user can re-click. If the IPC fails 3 times, the modal logs to console as a warning and treats itself as denied (matches the per-call approval timeout pattern).

### L2. Shell Stream Block

- **Loading (stream open, no output yet):** `<pre>` body shows `Waiting for output…` in `--color-text-muted` (12 px, italic) with the blinking `▍` cursor appended.
- **Empty (stream open, empty stdout AND empty stderr):** same as Loading.
- **Error:** if `isError === true`, the block adds `class="block-shell-stream block-result-error"` (the existing error class from `app.css:144-147` adds a red-tinted border). The footer shows `Exit code: <null> · aborted` when aborted, or `Exit code: <N>` when exited non-zero.
- **Stderr without stdout:** the stderr `<pre>` renders as the only body; the stdout `<pre>` is omitted (conditional `if stdout.length > 0 || exitCode === null`).

### L3. Denylist-Blocked Strip

- **Empty:** not applicable — the strip always carries the rule reason (the daemon always returns a reason on denylist match).
- **Error:** if the daemon's denylist match has no reason (shouldn't happen — defensive), the strip falls back to a single line: `Blocked by global denylist` (without the rule reason line).

### L4. Approval Modal Stack (concurrent approvals)

- **Empty:** not applicable — the stack only mounts when `pendingApprovals.size > 0`.
- **Error:** not applicable — see L1.

## Open Questions

These items need user decision before the planner begins; intentionally NOT locked.

1. **Modal mount animation.** Phase 5 ships static mount (no fade-in) for the security-critical "block-the-user" UX. Some users may prefer a brief fade. Confirm static mount is acceptable, or specify a fade duration (200-300 ms is typical).

2. **Auto-allow indicator wording.** Phase 5 says `Auto-approved from always-allow list (exact match).` Some users may prefer a shorter `Auto-approved.` Confirm the longer wording is acceptable, or specify a shorter one.

3. **Denylist rule reason visibility.** Phase 5 surfaces the matched rule's human reason (e.g. `sudo elevates to root`) on the second line of the denylist-blocked strip. Some users may consider this a security disclosure (an attacker who sees the denylist pattern can probe it). The reasons are already public in the daemon's source; the UI just exposes them. Confirm acceptable, or specify that the rule reason should be hidden (replaced with a generic `Command matched a dangerous pattern`).

4. **Always-allow list UI.** Phase 5 has no in-app UI to view or revoke always-allow entries; users must edit `<userData>/always-allow/<bot>.json` directly. Phase 9 may add a settings tab. Confirm acceptable for v1, or escalate to add a Phase 5 settings-tab minimum.

5. **Composer disabled state copy.** Phase 5 shows `Approve the pending shell command before sending another message…` while a modal is up. Some users may prefer a shorter `Waiting for approval…`. Confirm the longer wording is acceptable.

6. **Concurrent modal cap.** Phase 5 stacks modals indefinitely (modal #N at z-index 1500 + N * 100). If the LLM issues 10+ concurrent `exec_command` calls, the stack overflows the viewport. The `tools/call` maxTurns=10 cap (Phase 2) limits the total, but no per-message concurrent cap exists. Confirm no cap is needed, or specify a cap (e.g. `> 5 pending → queue the rest`).

7. **Approval timeout UX.** Phase 5 auto-denies after 5 min (daemon-side). The renderer gets no notification of the timeout; the user sees the modal disappear without an action. Confirm acceptable, or specify a "Approval timed out" toast/banner.
