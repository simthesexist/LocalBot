# Plan 04-03 — BotSettingsPage + RunHistoryTable + audit minimization + Playwright vertical smokes

**As a** Localbot user,
**I want to** open a full settings page for any bot (with General / Permissions / Schedule / Run History tabs), see the run history table for that bot paginated to the last 50 rows with new rows pushed live, and have the entire surface verified end-to-end against a fake M3 server,
**so that** the Phase 4 user story ("manage many bots — create, edit, delete, manually trigger, cancel — and see them all at a glance in the sidebar") is complete and CI-gated; Wave 1+2 closed the data surface and trigger flow, Wave 3 closes the read surface (settings page + run history) and the end-to-end test harness that proves no regressions land in Phase 5+.

## Objective

1. **BOTS_RUNS IPC** — main reads run history on demand (paginated). Renderer caches per bot.
2. **BotSettingsPage** — full settings page with 4 tabs (General / Permissions / Schedule / Run History); URL hash sync; tab keyboard nav; per-tab autosave.
3. **RunHistoryTable** — virtualized table with color-coded exitReason; scroll-to-bottom pagination; live push via EVENT_BOT_STATUS.
4. **Playwright vertical smokes** — bot-crud + multi-bot tests against a fake M3 server.
5. **Audit minimization** — bots/update + bots/trigger + bots/cancel audit params reduced to canonical non-PII fields (no error message text, no patch contents).

## Purpose

Wave 1+2 closed the write side of the Phase 4 surface (CRUD + trigger + cancel + run history writes). Wave 3 closes the read side (settings page + run history table) plus the test harness that proves the Phase 4 architecture holds under multi-bot + cancel scenarios. Without Wave 3, the user can create bots and trigger them but has no way to inspect history or configure a bot beyond the inline modal; Phase 5 (AGENT-09/10 — scheduled runs) and Phase 6 (cron parsing + tree re-rooting on workspace change) would both lack the surfaces they need.

## Output

- `BOTS_RUNS` IPC handler in main + `src/renderer/state/runs.ts` cache + `src/renderer/components/RunHistoryTable.tsx`.
- `src/renderer/components/BotSettingsPage.tsx` with 4 tabs + URL hash sync.
- Playwright `bot-crud.test.ts` + `multi-bot.test.ts` + extended `fake-m3-server.ts`.
- `playwright.config.ts` with `LOCALBOT_SMOKE_OK=1` gating.
- Audit minimization patches in `daemon/main.cjs`.
- 4 extended Vitest suites + 2 new Playwright suites (gated by `LOCALBOT_SMOKE_OK=1` for headed; CI runs the daemon-smoke variant).
- `npm run test:all` exits 0; `npm run build` exits 0.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| renderer -> IPC | All settings edits + run history reads go through preload `window.localbot.bot.{update,runs}` -> main IPC -> daemon JSON-RPC; renderer cannot read or write bot files directly |
| renderer -> URL hash | URL hash sync is renderer-only; the hash is NOT trusted by main or daemon; an attacker with renderer access could forge hash but cannot bypass the IPC layer |
| renderer -> file system (Playwright) | Playwright tests touch the actual `<userData>` directory under a temp dir; tests must clean up `<userData>/bots` after each test to avoid cross-test contamination |
| daemon -> LLM API | `streamBotTrigger` in fake-m3-server.ts emits canned chunks; tests must NOT call the real Anthropic API |
